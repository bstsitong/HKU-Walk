# HKU-Walk development conventions

## Language support is part of every feature

- User default: every new feature and its displayed content must automatically follow the selected interface language (Simplified Chinese, Hong Kong Traditional Chinese and English), unless the user explicitly requests a different translation behavior. This includes new screens, lists, details, messages, and content added through the administrator or submission forms. Do not infer an original-only display policy merely because text was entered by a user or administrator. Language support is part of completion, not a later follow-up task.
- All product-owned UI copy and built-in content must support Simplified Chinese, Hong Kong Traditional Chinese and English in the same change. Keep Chinese source text and English translations together in `locales/*-en.json`; do not edit generated `locales/messages.json` by hand.
- Use `Text`, `TextInput`, `Pressable`, `Image` and `Alert` from `ui.tsx`. Native imports used only as types or for keyboard control are fine. Translate accessibility hints and value text as well as visible labels.
- Use `t('第 {step} 步', { step })` for dynamic copy. Do not concatenate or interpolate translated prose. Keep source data or identifiers in state and translate at render time. Components computing translated values must subscribe to `useLanguage()`; memo dependencies must include the language.
- Preserve authored source text in storage and editing inputs; translate the display separately. `raw` is for editing/source previews, already-localized output, official brand names, URLs, identifiers, and content with an explicitly approved original-only display policy. It must not silently opt new content out of language switching. Keep names and identity-bearing codes accurate; do not invent translated identities.
- Published route titles, descriptions and step text, and place introductions must automatically follow the interface language, including future uploads and administrator edits. Reuse the shared automatic-content translation pipeline; key cached translations by content identity, source revision/text and target language, invalidate them when the source changes, and prevent results for a previous language from appearing after switching. Preserve source text, image URLs, ordering and room codes. New types of dynamic display content need the same language handling and switching checks before release.
- Explicit user exception: community posts retain their original display until the user taps the localized "Show translation" control. Preserve this behavior unless the user changes it; do not generalize it to other new features or content.
- New built-in data files must be imported by the app so the locale audit discovers their visible strings. Search aliases are not display copy. New or changed built-in guide articles need English bodies in `locales/guide-articles-en.json`; after updating the translation, update the matching normalized source SHA-256 in `locales/guide-source-revisions.json`. Keep Markdown links and page anchors unchanged.
- Run `npm run locales:prepare` to generate the dictionary and check coverage. `npm run locales:check` additionally rejects stale generated files. `node scripts/check-localization.cjs` exercises switching and missing-translation rejection. Metro start/export and OTA signing enforce the same language gate automatically; never bypass it for a release.
- If source or translations change after an Expo export, export again before signing. UI screenshots and device checks must be reported separately from static language validation.
